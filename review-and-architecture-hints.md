# Review and architecture hints: Rustrx

For anyone reviewing Rustrx: where the code comes from, how it is laid out, what is worth reading and what is boilerplate.

## Where the code comes from

Rustrx is not a port. It was written from scratch, starting with `1a4b274` (2026-11-09), on one branch, `main`. All of it is new work, so the reliable view is the tree itself, or `git log -p` for how it grew. Each commit message says what changed, why and what was not checked, and ends with an LLMGD line grading it. `docs/audits/` holds the audits (a dated narrative and a findings ledger each): every finding, its commit, and what is still open.

The app was written by an LLM (Claude), directed and tested by the author, who has not read the code. Everything here is a prototype until a reviewer owns it. That is the point of this file.

For a security review, start with [security-review-guide.md](security-review-guide.md): trust boundaries, secrets, untrusted input, earlier audits and open questions.

## Architecture

- `core/` is a Rust crate on matrix-rust-sdk 0.19 (the SDK of Element X): Client, sync, crypto, store, timelines, sending. It is cross-compiled outside the Sailfish SDK (`core/build-aarch64.sh`, cargo-zigbuild, `--locked`), because Jolla's Rust is too old for the SDK, and bundled as `lib/librustrx.so`.
- The boundary is six C functions (`core/src/lib.rs`, `src/rustrx_core.h`; start, command, stop, shutdown, the store key, the version): commands go in as JSON with a `"cmd"`, everything comes back as JSON events with an `"ev"` on one callback, on tokio threads (the text valid only during the call: `eventCallback` parses it without copying). There are no return values. Each account's core has its own runtime, two workers, at most 8 blocking threads kept 60 s idle, and three connections per store database (`consts.rs`: one the SDK keeps for writing, two readers). `core/src/protocol.rs` is the contract (one enum), and `docs/PROTOCOL.md` is written from it.
- `core/src/core/*.rs` is `impl Core`, split by domain: `commands.rs` (dispatch only), `session.rs` (login, restore, logout), `sync.rs` (sync, room list), `timeline.rs` (the open room, sending, the send queue), `threads.rs`, `state_reactions.rs` (reactions on state rows: the SDK's timeline keeps none for joins, profile and other state events, so the open room fetches each loaded state event's reactions once, follows new ones and redactions from the sync, and `react` toggles them there; the counts and the fetched reply originals stay for the last 10 rooms per account, fetched again at an open 10 minutes after their fetch), `rooms.rs`, `spaces.rs`, `knock.rs`, `moderation.rs` (what the room's power levels allow, and the owner, admin and moderator commands: roles, permissions, history, guests, encryption, the directory, addresses, the server access list, pins, upgrades, reports), `account.rs` (recovery, keys, devices; Clear media empties the SDK's media cache by one clean with an expiry of zero, then puts the retention policy back: the send queue's pending uploads are stored outside the policy and stay), `verification.rs`, `packs.rs` (custom emoji; what it asked the server is kept in memory and in the account's SDK store as custom values, a room's own packs shown at once and asked again behind after 24 hours, dropped by the state handler for a room's pack events; with the classic sync the packs are read from the store's room state; docs/EMOJI.md, "Where the packs come from"), `media_cache.rs` (the decrypted copies in `media/`: `get_media` serves an existing file by its name instead of fetching and rewriting it, writes through a temporary name and a rename, and a sweep once per process keeps `media/` under 300 MB, oldest first, `emotes/` left out), `push.rs`, `call.rs`, `qrlink.rs` (QR codes between devices: a scanned code, and letting a new device in from this one, which hands over its keys; the QR login that shows its own code stays in `session.rs`; the camera's pictures are read by `rustrx_decode_qr` in `lib.rs`). Shared state is one async mutex in `core.rs`. `serialize.rs` makes the JSON the UI gets. A timeline goes out as the order of its ids plus only the new or changed items (`TimelineDiff` in `serialize.rs`: an item is serialized again only when the SDK replaced its `Arc`, or its reader names were learned; own_read, thread unread, state reactions and kept reply originals go on top and are compared on their own); `TimelineModel::applyTimeline` keeps the items by id, checks stream and `seq`, and asks for `timeline_resync` when it lost track (docs/PROTOCOL.md, "Timeline events"). The room list goes out the same way (`RoomsDiff` in `serialize.rs`, fed by `rooms_task` in `sync.rs`, which already rebuilds only the rows the SDK's updates name: the order of all room ids plus the rows that differ from the ones sent; full at a stream's start, after a full rebuild that changed something, and on `rooms_resync` / `refresh_rooms`, which wake the list task through a per-core `Notify`); `RoomLists::applyRooms` keeps the rows not sent as the same QVariant, checks stream and `seq`, and asks for `rooms_resync` when it lost track (docs/PROTOCOL.md, "Room list events").
- `design/` holds standalone mockups for design work, not built into the app: `security-glance/` is the Account tab's security glance, runnable on a desktop with `qmlscene -I . main.qml` (stand-ins for the few Silica types it uses).
- `src/` is the C++ bridge. `Rustrx.cpp` re-posts each event to the GUI thread and is `rustrx` in QML. Beside it: the models (`RoomLists`, `RoomModel` (a room list that no view, Connections or binding follows takes its rows without signals, `watched()`; RoomLists passes unchanged rows on as the same QVariant, so the tab lists compare them by pointer; tested in tests/cpp/roommodel. Full events, a list whose unchanged rows changed their order, more changed rows than 16 or a quarter of the list, a tab setting, the filter and a new merged view sort every tab anew; both ways must give the same lists, signals and settings, tested in tests/cpp/roomsort `deltaAsFull`. The notification, invitation and unread signals go out once every list holds the update. `mergeAccounts` keeps each account's merged rows by room id with their sort fields and hands out the uids, so the merged view reads no row it already has; the merged list keeps no `roomInfo` (the accounts' own lists answer it)), `TimelineModel`, which formats each row's text once in C++), `Twemoji`, `Media`, `VoiceRecorder`, `ShareAdaptor` (share sheet target), `UnifiedPush` (D-Bus connector, `docs/PUSH.md`), `Handover` (the stand-in's handover file, each field checked before it is taken; tested in tests/cpp/exif and tests/cpp/png), `KeyboardSlide` (a slide-out keyboard's state from MCE, so Lock to portrait gives way while it is open), `Voip` (classic 1:1 calls: the m.call.* state machine, media through GStreamer's webrtcbin, the microphone through Speex's echo canceller and noise suppression (appsink, appsrc) with the far end's audio as reference; the room header shows the progress from `progressreport`), and the stripped copy goes when that fails, takes longer than three times the video or is not needed), `AecFrames` (the echo canceller's microphone and far-end frames in step, the far end's queue capped; - One binary, three modes (`src/main.cpp`), locked against each other by the bus name `net.mowerk.harbour-rustrx`, all in the same sailjail profile:
  - the app;
  - the stand-in (`RUSTRX_BACKGROUND=1`, `systemd/harbour-rustrx.service`), never with a window;
  - push wake (`RUSTRX_PUSH_WAKE=1`, D-Bus activation by the UnifiedPush distributor, one message, then exit).
- Login (`session.rs`), with no WebView and no Amber.Web.Authorization:
  - Where the server has an account service (MAS, matrix.org), OAuth 2.0 through the SDK (`login_oauth`). Rustrx registers itself as a native app, opens the service's page in the system browser and takes the code on a loopback port. The password never passes through Rustrx, and the session file keeps the client id.
  - Elsewhere, a password (`m.login.password`) or classic `m.login.sso` (`login_sso`): the sign-on page in the browser, and back with a login token.
  - With a QR code (`login_qr`, MSC4108, where the server has the rendezvous): this device shows the code, a logged-in one scans it, and the user types its two digits (`qr_check_code`). The other device hands over the keys.
- Calls: Element Call in a WebView with `qml/call-bridge.js` injected, and the SDK's widget driver behind it (`docs/CALLS.md`).

## Read these first

1. `core/src/lib.rs` and `src/Rustrx.cpp`: the thread hop. Nothing may touch Qt state from a tokio thread.
2. `core/src/core.rs` and `timeline.rs`: the state lock (the audit found it held across a network wait) and the send queue, including how a refused event is dropped at start.
3. `src/main.cpp`, `Handover.cpp` and the two systemd units: the three processes and who opens the store when.
4. `session.rs`, `session_file.rs` and `SecretStore.cpp`: the session file (sealed with the store key) and the store key.
5. `src/TimelineModel.cpp`: the HTML rewriting of message bodies, which comes from other people's servers.

## Skim

`qml/twemoji/` (Twemoji PNGs), `qml/emoji-data.js` (generated), `icons/`, `translations/`, most of `qml/pages/`, `Tunables.qml`, `Keys.h`, `consts.rs`, packaging.

## Worth questioning

- The tests are young (0.4.7). They hold the wiring between the three languages, the message HTML and the plain texts, the room order, and the core's command parsing; nothing yet exercises a live server, the three processes or Qt 5.6 itself. The audits' ledgers list every finding with its commit or the decision behind it.
- Without sailfish-secrets (community ports), the store is unencrypted, and so is `session.json` with the access and refresh tokens. With it, the key seals both (`core/src/core/session_file.rs`; a plain file of 0.5.0 and earlier is sealed at its first read), and a session that cannot be unsealed is a failed restore, tried again, never a logout. Since 0.8.2 the store opens with the key's bytes, not as a passphrase (`StoreSecret`, `store_config` in `session.rs`; one helper for every opener): each database's cipher, wrapped under a 200,000-round PBKDF2 until then, is rewrapped under an HKDF of the key at its first open, by the SDK, one row write per database, so a crash between two leaves a mix the next start finishes. The data keys stay as they were. `rustrx-key-based-<database>` records each one (log only, the open never depends on it); `rustrx-encrypted` keeps its bare fingerprint (std's `DefaultHasher`, which a toolchain may change), because builds before 0.8.2 remove the store when it is anything else; the stable one (FNV-1a, fixed in `session.rs`) is `rustrx-key-fingerprint` beside it, and only that one, or a database's AEAD seal refusing the key (`prove_store_key`), removes a store; an old fingerprint that does not fit proves nothing. Those builds cannot open a rewrapped store: a failed restore with Retry, the store kept, and this build opens it again. The SDK's media cache is capped at `MEDIA_CACHE_MAX_BYTES` (`limit_media_cache`), the SDK's defaults for the rest; uploads in the send queue are exempt.
- The debug log is on by default until 1.0. It holds room and user ids, never message texts or passwords. Check that claim in `DebugLog.cpp` and the core's tracing calls.
- The stand-in never gets a window, because lipstick 0.37.6 crashed when a process exited after hiding one. It is a workaround, not a fix.
- `MainPage.qml` and `SettingsPage.qml` import `Sailfish.Silica.private` for the tab view (one reason it is no Jolla Store app, besides the bundled core).
- Other people's text reaches StyledText only escaped (`markup.js`, `TimelineModel`), Labels default to plain text, the QML engines have no network, and links leave the app through one gate (`openExternal`). Try to break that.
- The room list's rows are kept light (0.8.2 audit): the unread badge, the favourite glow and its sparkle are Loaders made only for rows that show them, the preview line height and the badge digit are measured once on `MainPage`, which also sets the models' name emoji size (one value for every list, from a Label sized as the row's name) and each tab list's `previewMultiLine` (the rows had a Binding each), and the glow breathes only for a while: a glowing favourite coming into sight (inside its list's visible part with the page active and its tab current, after a new unread message, or with Rustrx back in front) starts `Tunables.favGlowBreaths` breaths, then the glow holds still at `Tunables.favGlowRest`, so nothing runs per frame while no row breathes. The picture's rounding is `Tunables.avatarRounding`, with dconf `debugAvatarRounding` for A/B runs: `layer` (a layer and `RoundMask` per row, an offscreen pass each), `texture` (`RoundMaskTexture` over the hidden Image, reading its texture with the crop as a uniform), `provider` (`image://rxavatar`, `src/AvatarProvider.h` with `RoundAvatar.h`: rounded once on the CPU with RoundMask's own edge, then a plain Image that the scene graph can batch; tests/cpp/roundavatar), `off` (square). The room name keeps Silica's Fade, which adds a layer only to names that overflow; the preview sets its own `elide` because Silica's choice from `lineCount` looped.

## Timing markers

Every line starts with `perf:` (`grep 'perf:'` in the debug log). They are at debug level, off unless `RUSTRX_PERF=1` is in the environment (an invoker start by hand, since sailjail drops it) or a file `perf-log` is in the data folder. On the C++ side that enables the logging category `rustrx.perf` (`src/Perf.h`); on the core's, the tracing target `rustrx::perf`, added to `RUSTRX_LOG` or the default filter (its lines arrive as `core: DEBUG rustrx::perf: <name> ...`, so `grep 'perf: rooms '` finds only the C++ line). `t=` is ms on one monotonic clock started on the first line of `main()`.

- Start-up steps, `perf: <step> t=`: `main` (0), `app` (application made, debug log installed), `twemoji` (the emoji names read, on a worker thread started there; `names`, `ms`), `bus` (the bus name taken, after any wait for the other process), `unifiedpush` and `voip` in the Rustrx constructor (the objects only: the distributor is asked without waiting, `distributor` when its answer is in; GStreamer is set up at the first call, `gst` with its `ms`, a line of its own then), `cores` (every account's core started), `rustrx`, `connector` (push connector and handover), `service` (Service.qml), `view`, `qml_completed` (harbour-rustrx.qml; it pushes the first page: MainPage when the shown account has a saved session, StartPage otherwise), `mainpage` (now inside setSource on a saved session, else after the login), `qml` (setSource returned), `show`, `frame` (the first frame swapped, the first page's), `notes_taken` (the old notifications taken over, after the first frame or at the first notification), `rooms_received` (the first `rooms` on the core's thread, any account), `rooms_applied` (the shown account's first `rooms` in every model), `delegate` (the first RoomDelegate), `settled` (the shown list's length then unchanged for 500 ms; `t` is when it last changed).
- `perf: startup <step>=<t> ... ms`: the steps above in one line, at info, once per window start, at `settled`. The `startup: ... after N ms` lines also give `ms since main`.
- `perf: rooms`: per applied `rooms` event, account, rooms (in the list), `changed` (rows that differ from the ones held), `sent` (rows the event carried, all on a `full` one), `full`, bytes (the event's size: the order plus the rows sent), the parse on the core's thread, the wait for the GUI thread (`queued_ms`), the time in the tab models, the merged view and the share targets (`lists_us`, `merged_us`, `targets_us`), `merged_view`, the part of `lists_us` spent in the handlers of the account's notification, invitation and unread signals (`signals_us`: Service.qml's notifications), and whether the account's lists and the merged view sorted every tab anew (`lists_sorted`, `merged_sorted`; 0: only the changed rows placed). `queued_ms` is taken when the event reaches the handler (until 0.8.2-4 it was taken after the apply and held `lists_us` and `merged_us` as well). (Until the room list went incremental, `same=1` marked a text identical to the last one; every event's `seq` differs now.)
- `perf: timeline`, `perf: thread_timeline`: per event for the open room or thread, items (the order's length), changed (items carried), full, bytes, `parse_us`, `queued_ms`; then `perf: set_items` with items (rows after), changed, inserted, removed, moved, delta (items carried, -1 for a full compare) and `us` (including the views' handlers that run at once).
- Opening a room, `open_ms` from `room_open`: `room_push` (the page pushed from the list or the dev hook), `room_page_scroll`/`room_page_auto`/`room_page_seek`/`room_page_jump` (an older page asked for while the chat moves, by itself, by the unread seek, by a jump), `room_open` (RoomPage made, openRoom), `room_snapshot` (the first `timeline`), `room_rows` (the model's count leaves 0), `room_packs` (`image_packs` arrived, again on each re-request), `room_positioned` (RoomPage's first `position()` done).
- The core: `emit` (ev, n, bytes, `ser_us` for the JSON text, `callback_us` for the UI's parse, with the hash when on) for `timeline`, `thread_timeline`, `rooms`, `image_packs` and `members`; `open_room` (`draft_ms`, `built_ms` after build_timeline); `timeline_pass` (items, sent (items carried, none when nothing changed and nothing is emitted), full, `prep_us` for replies, receipt names, thread marks and the own receipt, `json_us` for the diff); `rooms_build` (full: a full rebuild, rooms, rebuilt, reused, `sent=false` when no row changed and nothing went out, `build_us`, `sort_us`; `event_full`, `items` the rows the event carried); `listen_latest` (rooms, ms: the latest-event listeners registered beside the room list); `image_packs` (packs, requests, bytes, state_events, from_store, revalidate, ms; requests=0 when all of it came from the cache, from_store counts answers read from the SDK store (kept ones or the classic sync's state), revalidate=true when a room's kept packs are asked again behind the answer); `image_packs_revalidate` (changed, state_events, bytes, ms); `get_media` (cached, bytes, ms: cached=true without the SDK or a write); `room_members` (members, ms).

## How it was tested

By the author, as a daily client on the Jolla Phone 2026 (SailfishOS 5.2) and on the hybris Pro¹-X port, with two accounts (matrix.org, and tchncs.de with single sign-on); verification was tested against nheko. Before each handover, the LLM checked builds, `qmllint`, package contents and start logs on those phones.

Since 0.4.7 (see `docs/audits/2026-11-16-lifecycle-and-input.md`):

- `python3 -m pytest -q tests`: static and wiring checks, on every push (`.github/workflows/ci.yml`).
- `tests/cpp/run.sh`: QtTest suites against the host's Qt 5, on every push.
- `cargo test --locked` in `core/`: nightly (`.github/workflows/nightly.yml`), because matrix-sdk takes minutes to compile.

Every test says which planted bug it was proven against, and each commit names its plants.

**Proof gate** for a change to count as done: the three suites pass, the RPM builds in the Sailfish SDK (which also catches what Qt 5.15 accepts and Qt 5.6 does not), and the change was seen working on a phone. Commit messages say which of these did not happen.
